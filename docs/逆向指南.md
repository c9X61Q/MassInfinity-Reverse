# .NET JIT 劫持型代码虚拟化保护（DNGuard HVM 一类）逆向指南

> 本文是一次完整实战的方法论沉淀：从环境搭建、保护机制定位、反篡改绕过，
> 到**原始 IL 全量提取**、**方法身份绑定**、**元数据被摧毁后的重建**、**IL 回填**与**反编译**。
>
> 面向的是这一类保护：**保护器替换 JIT 入口，把真实 IL 只在运行时现场解密。**

---

## 0. TL;DR

| 问题 | 结论 |
|---|---|
| 这类保护堵住 IL 提取了吗？ | **没有** |
| 关键点 | 保护器替换了 `ICorJitCompiler::compileMethod`，但**仍把原始 IL 转发给真 JIT** |
| 怎么绕？ | Hook **原始 JIT 的 `compileMethod` 函数体**（不是被劫持的 vtable 槽），反篡改完全失效 |
| 覆盖率怎么保证？ | `RuntimeHelpers.PrepareMethod` 全量逼 JIT（本项目 52,948 个方法拿到 97.6%） |
| 名字/token 从哪来？ | `MethodBase.MethodHandle.Value` **就是** `MethodDesc*`，用它做 join 主键 |
| 元数据被抹了怎么办？ | locals 用占位签名重建；EH 按标准 `COR_ILMETHOD_SECT_EH` 扫；token 不假设稳定 |
| 剩下什么难？ | 虚拟化方法（逻辑在 VM 字节码里），需要反虚拟化 VM |

## 1. 目标识别

### 1.1 判定托管程序集

```python
import struct
d = open('target.dll','rb').read()
pe = struct.unpack('<I', d[0x3c:0x40])[0]; coff = pe+4; opt = coff+20
magic = struct.unpack('<H', d[opt:opt+2])[0]
dd = opt + (112 if magic == 0x20b else 96)
clr = struct.unpack('<I', d[dd+14*8:dd+14*8+4])[0]
print("PE", "x64" if magic == 0x20b else "x86", "托管" if clr else "原生")
```

### 1.2 识别保护器

```bash
strings -n 6 target.dll | grep -iE "DNGuard|ZYXDNGuarder|Confuser|Eazfuscator|VMProtect"
```

命中 `ZYXDNGuarder` / `CHVMEEInfo` / `CHVMEEProxy` → DNGuard HVM 系。

### 1.3 加密节区判定（别对高熵区做静态分析）

```python
import math, collections
d = open('target.dll','rb').read()
pe = struct.unpack('<I', d[0x3c:0x40])[0]; coff = pe+4
nsec = struct.unpack('<H', d[coff+2:coff+4])[0]; opt = coff+20
so = opt + struct.unpack('<H', d[coff+16:coff+18])[0]
for i in range(nsec):
    b = so + i*40
    nm = d[b:b+8].rstrip(b'\0').decode('latin1')
    vs, va, rs, ro = struct.unpack('<IIII', d[b+8:b+24])
    if rs == 0: continue
    data = d[ro:ro+rs]; c = collections.Counter(data); n = len(data)
    ent = -sum((v/n)*math.log2(v/n) for v in c.values())
    print(f"{nm:10s} {rs:>9,} B  熵={ent:.3f} {'← 疑似加密' if ent > 7.5 else ''}")
```

> **教训**：熵 ≈ 7.9 的节区（本例 `.hvm0`，3.06 MB）只能做运行时分析。
> 在那上面「找到」的函数和索引表全是随机数据上的幻觉。

### 1.4 落盘 IL 是什么形态（决定后面要不要运行时）

写一个 ECMA-335 元数据读取器（本项目 `tools/MassRecon` 即是），枚举全部 `MethodDef`：

```csharp
using var pe = new PEReader(File.OpenRead(dll));
var md = pe.GetMetadataReader();
foreach (var mh in md.MethodDefinitions) {
    var mdh = md.GetMethodDefinition(mh);
    if (mdh.RelativeVirtualAddress == 0) continue;          // abstract / pinvoke
    var il = pe.GetMethodBody(mdh.RelativeVirtualAddress).GetILBytes();
    // 判形态
}
```

本例实测：

| 落盘 IL 形态 | 数量 | 含义 |
|---|---|---|
| `72 xx..` `73 xx..` `7a`（`ldstr`/`newobj`/`throw`） | **52,159** | 保护器的抛错桩 —— 真实 IL 不在文件里 |
| 明文 IL | 474 | 未受保护（编译器生成的小方法等） |

**结论：真实 IL 只能从运行时拿。** 这一步是整个工程的分水岭。

## 2. 运行环境（反调试会拦住你）

保护器的 `<Module>.cctor` 一般带反调试。本例用窗口站可见性：

```asm
GetProcessWindowStation
GetUserObjectInformationA(..., UOI_FLAGS)
test WSF_VISIBLE
```

**后果**：SSH / 服务 / session 0 启动的目标会被直接拒绝。必须**在交互式桌面会话里跑**。

```bat
schtasks /create /tn MassDump /tr "C:\path\run.bat" ^
         /sc once /st 23:59 /ru <user> /rl highest /it /f
schtasks /run /tn MassDump
```

`/rl highest`（绕过 UAC 过滤令牌）+ `/it`（交互式会话）两个都必须要。

### 排错顺序（很省时间）

1. 先注入**空脚本** → 目标正常启动 = 保护器不检测注入本身；
2. 再 hook 保护器的 `compileMethod` → `InvalidProgramException` = 反篡改在保护自己的 hook 点；
3. 换成 hook 原始 JIT → 通了。

## 3. 定位 JIT 劫持

### 3.1 拿到被劫持的第一个槽

.NET 的 JIT 入口是 `ICorJitCompiler` 的 vtable[0]：

```js
const clrjit = Process.enumerateModules().find(m => m.name.toLowerCase() === 'clrjit.dll');
const getJit = clrjit.findExportByName('getJit');
const jitObj = new NativeFunction(getJit, 'pointer', [])();
const vt = jitObj.readPointer();
const cm = vt.readPointer();                       // 被劫持的 compileMethod
const owner = Process.findModuleByAddress(cm);     // → Mass.Runtime64.dll + 0x446b0
```

同时监控 `vt` 是否被改写 —— 本保护器是**原地改写 vtable 槽**，
所以要在目标启动早期采样，或者直接从 clrjit 的**静态 vtable**（.rdata）里读原值。

### 3.2 找原始 `compileMethod` 的地址

- 方法 A：目标启动**前**读 `jitObj.vtable[0]`；
- 方法 B：静态解析 —— clrjit.dll 的 `ICorJitCompiler` vtable 在 `.rdata`，
  vtable[0] 就是原始 `compileMethod`（本例 `clrjit.dll + 0xed430`）；
- 方法 C：直接在 clrjit 里找“典型 JIT 编译入口”的函数序言。

### 3.3 `compileMethod` 的参数布局（Windows x64）

```asm
; ICorJitCompiler::compileMethod(this, comp, info, flags, nativeEntry, nativeSizeOfCode)
rcx  = this            (ICorJitCompiler*)
rdx  = comp            (ICorJitInfo*)
r8   = info            (CORINFO_METHOD_INFO*)
r9d  = flags
[rsp+0x28] = nativeEntry**
[rsp+0x30] = nativeSizeOfCode*
```

`CORINFO_METHOD_INFO`（.NET 8，**总长 0x110**）：

```
+0x00  ftn         CORINFO_METHOD_HANDLE (= MethodDesc*)
+0x08  scope       CORINFO_MODULE_HANDLE
+0x10  ILCode      uint8_t*
+0x18  ILCodeSize  uint32
+0x1c  maxStack    uint32
+0x20  EHcount     uint32
+0x24  options
+0x28  regionKind
+0x30  args        CORINFO_SIG_INFO   (0x70)
+0xa0  locals      CORINFO_SIG_INFO   (0x70)
```

`CORINFO_SIG_INFO`（0x70）里要注意的：

```
+0x40  flags
+0x44  token
+0x48  scope
+0x50  pSig         ← 签名字节
+0x58  cbSig        ← 签名长度
```

> **实测发现**：本保护器交给 JIT 的 `locals.cbSig` **恒为 0**（100% 采样），
> 即它不提供局部变量签名 —— 这也解释了为什么用 `PrepareMethod` 批量编译时
> 大量方法会抛 `InvalidProgramException`（JIT 发现 IL 用了 `ldloc` 却没有局部变量）。

## 4. 全量提取

### 4.1 hook 点

```js
Interceptor.attach(clrjit.base.add(0xed430), {
  onEnter(a) {
    const info = a[2];
    const ftn  = info.readPointer();
    const ilP  = info.add(16).readPointer();
    const ilS  = info.add(24).readU32();
    const ms   = info.add(28).readU32();
    const eh   = info.add(32).readU32();
    // 落盘：ftn | ilSize | maxStack | eh | IL hex | ILCode 前后若干字节
  }
});
```

**别漏了几件事**：

| 坑 | 后果 |
|---|---|
| spawn 注入时 `clrjit.dll` 还没加载 | 轮询 `setTimeout` 等模块出现 |
| 脚本跑完 `frida-inject` 退出会杀掉目标 | 末尾 `setInterval(()=>{},3000)` 保活 |
| Frida 17 移除了全局 `Module.findExportByName` | 用模块实例的 `findExportByName` |
| ILCode 之后可能跨界读 | `readByteArray` 递减长度重试，别让一次异常打断采集 |
| `ldstr`（`0x72`）和 `calli`（`0x29`）、`ldftn`（`FE 06`）也是 token 操作数 | 做 IL 比对时忘了掩码会得到假差异（本项目踩过） |

### 4.2 让所有方法都被 JIT —— `RuntimeHelpers.PrepareMethod`

只跑目标本身，覆盖率取决于「跑过哪些代码」（本例只有 22.5%）。
要拿全，就自己写一个**覆盖器**，借目标自带的运行时启动：

```csharp
// ① 载入全部目标程序集（只喂托管的 PE：原生 DLL 交给 Assembly.LoadFrom 会 c0000005）
var a = Assembly.LoadFrom(dllPath);

// ② 关键：显式执行模块初始化器，保护器的 JIT 劫持是在 <Module>.cctor 里装的
RuntimeHelpers.RunModuleConstructor(a.ManifestModule.ModuleHandle);

// ③ 全量逼 JIT
foreach (var t in a.GetTypes())                 // 泛型类型定义要先 MakeGenericType
  foreach (var m in t.GetMethods(F | DeclaredOnly)) {
      var target = m.ContainsGenericParameters ? 约束求解后实例化(m) : m;
      RuntimeHelpers.PrepareMethod(target.MethodHandle);
  }
```

**启动方式**：目标是自包含 .NET 应用时，apphost 内嵌了固定的 dll 名，
把 exe 改名没用。做法：复制整个目标目录，把真身改名 `X.dll.real`，
让自己的程序顶替 `X.dll`，用原 apphost 启动；覆盖器扫 `Mass.*.dll` + `Mass.*.dll.real` 两种后缀。

**踩过的坑**：

| 坑 | 现象 | 解法 |
|---|---|---|
| `Assembly.LoadFrom` 喂了原生 DLL | `c0000005`，`Mass.Runtime64.dll_unloaded` | 先用 `PEReader.HasMetadata` 过滤；原生 DLL 绝不能走 LoadFrom |
| 覆盖器枚举不到受保护类型 | `PrepareMethod` 编出来全是抛错桩 | 忘了 `RunModuleConstructor` |
| 泛型实例化大面积 `ArgumentException` | 约 1/3 方法失败 | 按泛型约束挑类型实参（`struct`→`int`、基类约束→该基类、兜底 `object`），失败再退全 `object`/全 `int` |

### 4.3 方法身份：`MethodDesc*` 做主键（最重要的一步）

`compileMethod` 只给 `MethodDesc*`。少有人注意：**托管侧能直接拿到同一个指针**。

```csharp
long md = methodBase.MethodHandle.Value.ToInt64();   // 就是 MethodDesc*
```

于是把采集拆成两路：

```
Frida  侧：ftn(MethodDesc) | ilSize | maxStack | eh | IL hex
托管侧 ：md | MVID | token | 类型 | 方法 | 签名        → map.txt
离线    ：按 MethodDesc join
```

**为什么不要用「顺序对齐」**：曾经试过「写一条身份 → 调 `PrepareMethod` → 收一条 IL」的
顺序文件通道，看似严格串行，实际有三个破绽：其他线程并发 JIT 会插进来、
tiering 会让同一方法编译多次、`PrepareMethod` 对已编译方法是 no-op。
改用**键表 join** 后这些问题全部消失。

> ⚠️ `MethodDesc` 地址每次进程都变 —— **`map.txt` 和 IL dump 必须来自同一次运行**。
> 这个坑本项目踩过：混用两次运行的数据，join 命中率从 94.6% 掉到 4%。

### 4.4 IL 形态分类

| 形态 | 字节模式 | 含义 |
|---|---|---|
| `real` | 其他 | 真实原始 IL ✅ |
| `throw` | 11 字节 `72 xx 73 xx 7a` | 抛错桩（保护器没解密） |
| `vm` | 16 字节 `20 p 20 i 28 t 2a` | HVM 桩：`ldc.i4 progid; ldc.i4 idx; call VM派发器; ret` |
| `tail` | 6 字节 `28 xx 2a` | `call X; ret` 转发桩 |

## 5. 元数据被摧毁后的重建

### 5.1 局部变量签名

**现象**：`CORINFO_METHOD_INFO.locals.cbSig == 0`（100% 采样），
元数据里的 `StandAloneSig` 整表被填 `0xCC`。

**判据校准技巧**（比背结构体布局靠谱）：IL 里 `ldloc/stloc` 用到的最大序号是硬约束 ——
真签名的局部变量个数必须 `> maxloc`，且签名字节要**精确消耗完** `cbSig`。
枚举 `(locals 基址, pSig 相对偏移)` 全组合做校验，正确组合会压倒性胜出。
（本项目就是这么确认了「保护器干脆不给」这个结论。）

**兜底**：按 IL 用到的槽位数造 `count` 个 `ELEMENT_TYPE_OBJECT (0x1C)` 的占位签名，
类型交给反编译器从使用点推断。DNGuard 同时会摧毁 `LocalVarSigTok` 指向的 blob，
所以不要指望从元数据读。

### 5.2 异常处理子句

IL blob 的标准布局是 `[头][代码][4 字节对齐][COR_ILMETHOD_SECT_EH]`：

```
Kind(1)  0x01=EHTable；0x40 置位=肥子句
DataSize 小段：1 字节；肥段：3 字节。**含段头本身**（小段 4、肥段 6）
Reserved 2 字节
子句
   小(12B): u16 flags | u16 tryOff | u8 tryLen | u16 hOff | u8 hLen | u32 classToken
   肥(24B): u32 flags | u32 tryOff | u32 tryLen | u32 hOff | u32 hLen | u32 classToken
```

**校验**：`flags & 7 ∈ {0,1,2,4,5}`、`tryLen/hLen > 0`、`tryOff+tryLen ≤ ilCodeSize`、
`hOff+hLen ≤ ilCodeSize`、子句条数 == `EHcount`。

> 注意：保护器把 IL 拷进自己的缓冲时**不一定把 EH 段一起拷**（本例 409 个含 EH 的方法
> 只恢复了 278 个）。找不到就退回 hook `comp->getEHinfo`。

### 5.3 `getEHinfo` 不是必须的，但要知道怎么做

`comp` 是 `ICorJitInfo*`。**先确认它的 vtable 落在哪**：

```js
Process.findModuleByAddress(comp.readPointer())   // 落在 coreclr.dll = 真对象，可直接调
                                                  // 落在保护器模块  = 可能是 thunk，逐索引调用会 AV
```

若落在 coreclr，可以直接按标准索引调 `getMethodName` / `getEHinfo`。
若不是，静态反汇编 clrjit.dll，从 EH 处理代码里读那个 `call qword ptr [rax+disp]` 得到 vtable 索引。

### 5.4 token 稳定性

保护器会打乱 `MethodDef` 表顺序；回填工具（dnlib 等）写盘时又会**归一化表顺序**，
于是 IL 里的 token 操作数会被整体重写（长度不变、字节不同）。

**结论**：
- 定位方法用 **(MVID, token)**（源模块）或 **(类型全名, 方法名)**（输出模块），别混用；
- 做字节级验证时，必须先**把 token 操作数掩码**（`ldstr`/`calli`/`ldftn`/`ldvirtftn` 也算 token），
  否则会得到 100% 假差异。

## 6. 回填与反编译

### 6.1 用 dnlib 回填

别自己写 IL 操作数解析 —— **把 `[fat header][IL][对齐][EH 段]` 合成为标准
`COR_ILMETHOD` 镜像，交给 dnlib 的 `MethodBodyReader`**，token/参数/局部变量索引它全都会处理：

```csharp
// fat header：Flags 低 2 位 = 0b11(fat)，bit3 = MoreSects，bit4 = InitLocals，
//             **bit12-15 = 头长度(4 字节单位) = 3**   ← 漏了它就是「0 条指令」
bw.Write((ushort)(0x3003 | (hasEh ? 0x8 : 0) | (localsCount > 0 ? 0x10 : 0)));
bw.Write((ushort)maxStack);
bw.Write((uint)il.Length);        // CodeSize（ECMA 里这个字段在 MaxStack 之后！）
bw.Write(0u);                     // LocalVarSigTok
bw.Write(il);
while ((ms.Length & 3) != 0) bw.Write((byte)0);
if (hasEh) bw.Write(ehSection);

var reader = new MethodBodyReader(mod, fac.CreateReader(0, len), method);
reader.Read();
method.Body = new CilBody(initLocals, reader.Instructions, reader.ExceptionHandlers, locals) {
    MaxStack = maxStack, KeepOldMaxStack = true
};
```

**必须要的兜底**（保护器摧毁了部分元数据，未回填方法里会有操作数为空的指令）：

```csharp
// ① 剔掉指令列表里的 null 占位
// ② 操作数为空 / 分支目标不在本体内 → 该指令降级为 nop
```

写盘时：

```csharp
var wo = new ModuleWriterOptions(mod);
wo.MetadataOptions.Flags |= MetadataFlags.KeepOldMaxStack;   // 否则 maxstack 校验会拒绝写盘
mod.Write(outPath, wo);
```

### 6.2 常见写盘报错对照

| 报错 | 原因 | 解法 |
|---|---|---|
| `Error calculating max stack value` | dnlib 重新校验 maxstack | `KeepOldMaxStack`（body + MetadataOptions 两处） |
| `Instruction operand is null` | 指令操作数为空 | 该指令降级 `nop` |
| `Instruction is null` | 指令列表里有 null 占位 | 剔除 null 并修正指向它的分支 |
| 写出来的方法体全是同一个 | reader 用错重载（`(mod, reader, method)` 会去读模块里原有的体） | 用 `(opResolver, codeReader, ehReader, parameters, gpContext)` |
| reader 返回 0 条指令 | fat header 的 Flags 没写头长度 | `0x3003` |
| 反编译出的字面量是空串 | `#US`/`Constant` 堆被摧毁 | 只能运行时抓，或在 hook 里顺带 dump |

### 6.3 反编译

```bash
ilspycmd -p -o src/ <回填后的程序集>        # 每个程序集一个可编译项目
```

## 7. 验证（很重要，别跳）

三层验证，从硬到软：

1. **字节级**：重读输出、比 IL 字节。注意 **token 会被重映射**，直接比会全错。
2. **token 掩码后的字节级**：把 `ldstr`/`calli`/`ldftn`/`ldvirtftn`/所有 `InlineTok` 的 4 字节清零再比 —— 这是**本项目使用的判据**。
3. **指令流级**：解码成 `(opcode, operand-kind)` 序列比对（能容忍宏优化）。

定位方法时按 **(类型全名, 方法名)**，别按 token；同名重载会让比对出现「假差异」，
评估时要按「期望方法能不能在候选池里找到等价项」而不是一对一硬比。

## 8. 踩坑清单（合集）

| # | 坑 | 现象 / 后果 | 解法 |
|---|---|---|---|
| 1 | 在高熵加密节区做静态分析 | 「找到」的函数与索引表全是幻觉 | 加密区只做运行时分析 |
| 2 | `0xFE` 前缀按 1 字节解码 | IL 整段错位 | 变长前缀表 |
| 3 | `switch` 只消费 8 个字节 | 错位几万字节 | 消费全部 k 个目标 |
| 4 | `throw` 写成 `0x2A` | 形态分类全错 | `throw = 0x7A`，`ret = 0x2A` |
| 5 | `Assembly.LoadFrom` 原生 DLL | `c0000005`（DllMain 卸载时崩） | 先查 `PEReader.HasMetadata` |
| 6 | 忘了 `RunModuleConstructor` | 编出来全是抛错桩 | 显式执行模块初始化器 |
| 7 | 用顺序通道做身份绑定 | 并发 JIT/tiering 让数据错位 | 用 `MethodDesc` 键表 join |
| 8 | `map` 与 IL dump 不同批次 | join 命中率暴跌 | 强制同一进程同一批次 |
| 9 | fat header 漏 `CodeSize` / 头长度 | dnlib 读到 0 条指令 | Flags = `0x3003`，字段顺序 `Flags|MaxStack|CodeSize|LocalVarSigTok` |
| 10 | 忘了掩码 `ldstr` 的 token | 100% 假差异 | token 掩码集合要含 `ldstr`/`calli`/`ldftn` |
| 11 | SSH/session 0 启动目标 | 反调试直接拒绝 | `schtasks /rl highest /it` 在交互式会话跑 |
| 12 | 脚本结束就退出 | 目标被一起杀掉 | 保活 `setInterval` |
| 13 | 在加密节区做「函数识别」 | 得到一堆假函数 | 只看明文节 + 运行时 |

## 9. 还剩什么

虚拟化方法（本例 7,847 个，占 15%）的真实逻辑在 VM 字节码里。继续做需要：

1. **dump 出 VM 程序明文**：保护器总要解密才能解释执行，优先找「取程序」那一步，
   或在进程内存里按 `byte[]` 布局扫那几段状态机对应的数据；
2. **状态机 CFG**：引擎是巨型生成式 IL（本例 7 个，最长 329,681 字节），
   形态是 `switch` 状态机 —— 读出 `switch` 的全部目标就是状态入口，
   handler 结尾的 `ldc.i4 <next_state>` 常量就是状态转移；
3. **handler 聚类提 ISA**：按「是否读 VM 程序数组」区分取指 / 执行 / 超算子，
   取指里读到的常量就是 opcode；
4. **反虚拟化输出**：解码成 IL 后回填，或输出 IR 让反编译器做优化。

因为引擎本身是 **IL**（不是原生汇编），这一步比传统原生 VM 反虚拟化省掉约 60% 工作量：
没有寄存器别名、没有标志位、指令宽度确定的栈机，直接写抽象解释器即可。
